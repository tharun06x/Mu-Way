## 1. What This System Does

ICRS is a **personalised career roadmap generator** built for the [Mulearn](https://mulearn.org) platform. Given a user's MUID (Mulearn User ID) and their dream job role (e.g. "Backend Developer"), the system:

1. Looks up **all tasks the user has ever submitted** on the Mulearn platform
2. Computes their **skill mastery level** across 24 technical domains (AI, DSA, DevOps, etc.)
3. Calculates a **skill gap** — how far they are from the requirements of their chosen role
4. **Recommends tasks** from Mulearn's task catalog, ordered by what will close their biggest gaps fastest
5. Packages those recommendations into a **week-by-week roadmap** with difficulty progression

The output is a structured JSON + Streamlit UI showing which tasks to do, in which week, and why.

## 4. Data Flow — End to End

### Input: `query.xlsx`
This is the raw data export from the Mulearn platform. Each row is one task submission by one user:

| Column | Description |
|---|---|
| `user_id` | e.g. `tharuntomy@mulearn` |
| `task_name` | e.g. `"Build For Team"` |
| `hashtag` | e.g. `#ge-intro-to-github` |
| `karma` | Points awarded for this submission |
| `is_approved` | 1 = approved by admin, 0 = pending/rejected |
| `difficulty_level` | 1 (beginner) → 4 (expert) |
| `domain` | Raw hashtag string — needs mapping |
| `created_at` | Submission timestamp |

> **Note:** The data is noisy. About 40% of submissions are community engagement tasks (karma, events, volunteering) that have no technical value. These are filtered out using the `ignored` domain in `taxonomy.yaml`.

### How a Hashtag Becomes a Domain
`#ge-intro-to-github` → tokenised → `['ge','intro','to','github']` → structural tokens removed (`ge`, `to`) → remaining tokens `['intro','github']` → matched against `taxonomy.yaml` → **`tooling`** domain (because `github` is in `tooling` tokens).

The function `hashtag_to_domain()` in `problem1.py` does this.

## 5. Pipeline Stages

### Problem 1 — Feature Engineering (`problem1.py`)
**Input:** Raw user submissions from `query.xlsx`  
**Output:** 40-column feature vector per user

Key features computed per user:
| Feature | Formula |
|---|---|
| `mastery_{domain}` | `approved_karma / (total_karma + ε)` per domain, clamped to [0,1] |
| `task_count_{domain}` | Count of submitted tasks per domain |
| `interest_{domain}` | `task_count / total_tasks` per domain |
| `global_approval_rate` | `approved_count / total_count` |
| `optimal_difficulty` | Weighted avg difficulty of approved tasks, **clamped to [1.0, 4.0]** |
| `engagement_score` | Recency + frequency composite |

> **Bug fixed:** `optimal_difficulty` was previously unclamped, allowing values outside [1,4] which broke difficulty progression.

**Cold-start handling:** If a user has no submissions, all masteries = 0, optimal_difficulty = 1.5 (beginner), and interest = uniform across all domains.

---

### Problem 2 — Skill Gap Modeling (`problem2_runner.py`)
**Input:** User mastery dict + dream role  
**Output:** `career_gap`, `alignment_score`, per-domain gap breakdown

**Formula:**
```
raw_gap(domain) = max(0, required_mastery - current_mastery)
weighted_gap(domain) = raw_gap(domain) × role_weight(domain)
career_gap = Σ weighted_gap(domain)                    [range: 0 → 1]
alignment_score = 1 - career_gap                       [range: 0 → 1]
```

**Gap Tiers:**
| Tier | Condition | Meaning |
|---|---|---|
| `CRITICAL` | weighted_gap > 0.04 | Must fix urgently |
| `MODERATE` | weighted_gap > 0.01 | Should address |
| `MARGINAL` | weighted_gap > 0.001 | Minor gap |
| `MET` | weighted_gap = 0 | Requirement satisfied |

**Fallback:** If the dream role isn't in `ROLE_REQUIREMENTS`, defaults to `'Full Stack Developer'`.

---

### Problem 3 — Task Ranking & ML Model (`problem3_runner.py`)
**Input:** User features + task features  
**Output:** Ranked list of recommended tasks with scores

This is the core ML stage. It has two modes:

**Training mode** (`run_ranking_pipeline()`):
1. Loads all user features from the feature store
2. Loads all tasks from `query.xlsx` (filtered through taxonomy)
3. Creates (user, task) pairs matched by domain
4. Engineers advanced features (see below)
5. Computes rule-based scores as training labels
6. Trains a `GradientBoostingRegressor` (sklearn)
7. Saves model to `output/ranking_model.pkl`

**Inference mode** (`recommend_for_user()`):
1. Takes one user's feature dict
2. Creates pairs with all tasks in catalog
3. Engineers same features
4. If user has ≥5 submissions AND model is loaded → ML score
5. Otherwise → rule-based score (same formula as training labels)

**7 ML Features:**
| Feature | What it captures |
|---|---|
| `gap_score` | How much does this task's domain close the user's gap? |
| `interest_score` | Has the user shown interest in this domain? |
| `community_approval` | How popular is this task (normalised submission count)? |
| `difficulty_suitability` | Is task difficulty near user's optimal level? |
| `gap_interest` | gap_score × interest_score (interaction term) |
| `approval_probability` | User's historical approval rate |
| `task_count_in_domain` | User's activity level in this domain |

> **Bug fixed:** `task_role_relevance` and `domain_importance` were always constant 1.0 — zero signal. Removed.

**Stale model guard:** On load, the model's `feature_names` are compared against current `FEATURE_NAMES`. If they differ (e.g. after a bug fix removed features), the model is discarded and rule-based scoring is used, avoiding crashes.

---

### Problem 4 — Roadmap Sequencing (`problem4_runner.py`)
**Input:** Ranked task list + career gap data  
**Output:** Week-by-week roadmap

Steps:
1. **Urgency assignment:** Tasks from CRITICAL gap domains get `urgency_order=1`, MODERATE=2, MET=3
2. **Domain task cap:** Maximum 4 tasks per domain in the pool — prevents any one domain flooding the roadmap
3. **Sort:** `weighted_gap DESC` → `domain_priority ASC` → `difficulty_order ASC` → `score DESC`
4. **Difficulty progression:** Within each domain, difficulty only increases by max +1 level per step. Prevents jumping from Beginner to Expert tasks.
5. **Week scheduling:** Tasks are packed into weeks using a time budget (`MINUTES_PER_WEEK`)
6. **Health score:** Fraction of CRITICAL gaps addressed in the roadmap

> **Bug fixed:** Old sort was by domain_priority index (positional), not actual weighted_gap. A domain at position 4 (testing_qa) with a small gap was getting more tasks than domain at position 3 with a huge gap.

---

### Problem 5 — Drift Monitoring (`problem5_runner.py`)
**Input:** Current roadmaps + historical data  
**Output:** `health_report.json`

Monitors for:
- Drop in average roadmap health score
- Shift in domain distribution of recommendations
- Unusual score distributions (potential data drift)

Triggers a retraining flag if degradation is detected.

## 6. Configuration Deep Dive

Everything configurable lives in **`config.py`**.

### Role Requirements
Each role has a dict of `{domain: (required_mastery, role_weight)}` tuples:
```python
'Backend Developer': {
    'core_programming': (0.90, 0.35),   # need 90% mastery, 35% of total gap score
    'dsa':              (0.85, 0.30),
    'web_dev':          (0.75, 0.20),
    'devops':           (0.65, 0.10),
    'testing_qa':       (0.70, 0.05),
}
```
**Rule:** All weights must sum to exactly **1.0** (verified in tests).

## 7. Domain Taxonomy

File: **`config/taxonomy.yaml`**

This YAML file maps hashtag tokens → domains. It's the most important file for data quality.

### Structure
```yaml
domain_token_map:
  ai:
  - ml
  - tensorflow
  - pytorch
  - neural
  web_dev:
  - react
  - javascript
  - node
  - html
  ...
  ignored:            # ← These tasks are NEVER recommended
  - daily-chat-karma
  - musprint
  - karma
  - volunteering
  ...
structural_tokens:    # ← Stripped before matching (platform prefixes)
- cl
- ge
- evn
```

### How Token Matching Works
Given hashtag `#cl-web-markingupaletter`:
1. Strip `#` → `cl-web-markingupaletter`
2. Split by `-` → `['cl', 'web', 'markingupaletter']`
3. Remove structural tokens → `['web', 'markingupaletter']`
4. Match each token against `domain_token_map` first-match wins
5. `web` → matches `web_dev` → domain = **`web_dev`**

### Why `ignored` Exists
Mulearn has 700+ tasks but ~40% are community engagement (karma farming, event participation, social tasks). These get assigned domain=`ignored` and are **filtered out before the ML model ever sees them**. Without this, users would get "daily-chat-karma" on their Backend Developer roadmap.

## 8. ML Model

**Algorithm:** `GradientBoostingRegressor` (sklearn)
- n_estimators: 100
- max_depth: 4  
- learning_rate: 0.1

**Training data:** Synthetic (user, task) pairs from all platform submissions, with rule-based scores as labels. This means the model learns to replicate and generalise the rule-based scoring, while also capturing interaction patterns in the data.

**Prediction threshold:** ML scoring only activates if user has **≥5 submissions**. Below that, rule-based scoring is used (cold-start).

**Model file:** `output/ranking_model.pkl` — serialised with `pickle`. Contains the GBR + `feature_names` list for validation.

**Retrain trigger:** Run `python problem3_runner.py` — takes ~2-5 minutes. Automatically saves the new model.

## 9. The Streamlit App

File: **`app.py`** (UI) + **`roadmap_app.py`** (logic)

### User Flow
```
Sidebar: Enter MUID + Name + Dream Role
    ↓ Click "Generate Roadmap"
app.py → calls roadmap_app.generate_roadmap()
    ↓
Shows:
  - Readiness score (0-100%)
  - Gap tier (CRITICAL / MODERATE / MET) per domain
  - Week-by-week task cards with:
      • Task name
      • Domain icon
      • Difficulty label
      • Urgency badge
      • Score
```

### Data Loading
```python
@st.cache_resource   # ← Cached on first load, never reloaded during session
def load_pipeline_data():
    user_data, task_data, _ = DataLoader().load_all()
    return user_data, task_data
```
This means `query.xlsx` is read **once** when the app starts and cached in memory. All subsequent requests are instant.

### Cold Start (New User / Unknown MUID)
If the MUID isn't in `query.xlsx`, the system uses default features:
- All domain masteries = 0
- optimal_difficulty = 1.5 (beginner)
- Uniform interest across all domains

This produces a valid beginner-level roadmap.

## 10. Mathematical Formulas

### F1 — Domain Mastery
```
mastery(domain) = Σ(approved_karma_in_domain) / (Σ(total_karma_in_domain) + ε)
```
Clamped to [0, 1]. `ε = 1e-9` to avoid division by zero.

### F2 — Optimal Difficulty
```
optimal_difficulty = Σ(difficulty × karma) / Σ(karma)   for approved tasks
```
**Clamped to [1.0, 4.0]** — prevents values outside the valid 1-4 difficulty scale.

### F3 — Weighted Career Gap
```
weighted_gap(d) = max(0, required_mastery(d) - current_mastery(d)) × role_weight(d)
career_gap = Σ weighted_gap(d)
alignment_score = 1 - career_gap
```

### F4 — Rule Score (also used as ML training label)
```
gap_boost     = gap_score × interest_score        (gap-interest interaction)
base_score    = 0.35×gap_score + 0.25×interest_score + 0.20×community_approval
              + 0.15×approval_probability + 0.05×difficulty_suitability
popularity_bonus = min(0.10, community_approval × 0.10)    ← capped at 10%
rule_score    = base_score + popularity_bonus
```
> **Bug fixed (F16):** Popularity boost was uncapped, allowing it to override skill-gap scores entirely. Now hard-capped at 10%.

> **Bug fixed (F13):** Weights in rule_score were inconsistent with ML training labels. Now aligned: gap(0.35), interest(0.25), approval(0.20), approval_prob(0.15), difficulty(0.05).

## 11. Known Design Decisions & Trade-offs

| Decision | Rationale | Trade-off |
|---|---|---|
| `query.xlsx` as data source | No database needed, simple deploy | Stale data until file is updated |
| Synthetic training data | No ground truth "good roadmap" labels exist | Model learns rule-based patterns, not human-validated quality |
| 4 tasks per domain cap | Prevents domain flooding | May miss edge cases where one domain truly needs 8+ tasks |
| `@st.cache_resource` | Fast multi-user access | 13MB Excel held in RAM always |
| GBR not XGBoost | sklearn is pre-installed everywhere | Slightly slower training, similar accuracy |
| Rule-based fallback | Works without a trained model | Less personalised recommendations for new users |

## 12. How to Run Locally

### Prerequisites
- Python 3.10+
- `query.xlsx` in project root

### Setup
```bash
git clone <repo-url>
cd rdmp
python -m venv .venv
source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### Run the App
```bash
streamlit run app.py
```

### Run Tests
```bash
pytest tests/ -v
```
All 9 tests should pass.

### Run the Full Batch Pipeline (optional)
```bash
python main.py
```
This runs P1 → P5 sequentially and writes output files.

## 13. How to Retrain the Model

Run this after any change to:
- `config/taxonomy.yaml` (domain mapping changes)
- `config.py` (role weights, domain list)
- `problem1.py` or `problem3_runner.py` (feature engineering)
- When new data is available in `query.xlsx`

```bash
source .venv/bin/activate
python problem3_runner.py
```

Output:
```
✓ Model saved → output/ranking_model.pkl
✓ Metadata saved → output/model_metadata.json
```

The running Streamlit app will pick up the new model on its **next cold start** (app restart or cache clear).

## 14. Deployment (Hugging Face Spaces)

### Why HF Spaces
- **Free tier: 16 GB RAM** — no OOM risk from query.xlsx
- Never sleeps (unlike Render free)
- Auto-deploys from git push

### Files Required on HF Spaces
| File | How it gets there |
|---|---|
| All `.py` files | Normal git commit |
| `config/taxonomy.yaml` | Normal git commit |
| `requirements.txt` | Normal git commit |
| `README.md` (HF header) | Normal git commit |
| `.streamlit/config.toml` | Normal git commit |
| `query.xlsx` (13 MB) | Git LFS |
| `output/ranking_model.pkl` (247 KB) | Git LFS |

### Deploy Steps
```bash
# 1. Install Git LFS
sudo apt-get install -y git-lfs
git lfs install
git lfs track "*.pkl" "*.xlsx"
git add .gitattributes

# 2. Retrain model
python problem3_runner.py

# 3. Commit data + model
git add query.xlsx output/ranking_model.pkl output/model_metadata.json
git commit -m "add data and model for deployment"

# 4. Create Space at huggingface.co/new-space (SDK: Streamlit)
git remote add hf https://huggingface.co/spaces/USERNAME/SPACE_NAME
git push hf tt:main
```

## 16. Glossary

| Term | Meaning |
|---|---|
| **MUID** | Mulearn User ID (e.g. `tharuntomy@mulearn`) |
| **Domain** | Technical skill area (e.g. `web_dev`, `dsa`, `devops`) |
| **Mastery** | Score 0–1 representing how skilled the user is in a domain |
| **Career Gap** | Weighted sum of how far the user is from all role requirements (0=perfect, 1=complete beginner) |
| **Alignment Score** | `1 - career_gap` — higher is better |
| **Readiness %** | `alignment_score × 100` |
| **CRITICAL** | Gap tier where user has a large deficit in an important domain |
| **Cold Start** | User with < 5 submissions — system uses default features |
| **GBR** | Gradient Boosting Regressor — the ML algorithm used for scoring |
| **Rule Score** | Weighted formula scoring tasks without ML (used as fallback + training label) |
| **LFS** | Git Large File Storage — needed to commit files > 10MB to git |
| **Hashtag** | Mulearn task identifier (e.g. `#ge-intro-to-github`) |
| **Structural Token** | Platform prefix stripped before domain matching (`ge`, `cl`, `evn`) |
| **Ignored Domain** | Tasks mapped here are filtered out before training/recommendation |
